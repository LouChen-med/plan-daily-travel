# plan-daily-travel

为多地点、固定到达时间或跨城衔接的行程查询交通与住宿，计算门到门耗时、最晚出发和缓冲，并模拟延误30分钟。适用于日程有多个约束的任务；简单问路通常直接使用Prompt即可。

## 查询网站

| 项目 | 首查 | 补充及核对 |
|---|---|---|
| 高铁 | [12306](https://www.12306.cn/index/) | [携程](https://www.ctrip.com/)火车票频道；余票和铁路规则以12306目标日期核对 |
| 机票 | [携程机票](https://flights.ctrip.com/online/channel/domestic) | [去哪儿](https://www.qunar.com/)机票频道比较，实际承运航司官网核对 |
| 酒店 | [去哪儿](https://www.qunar.com/)酒店频道 | [携程酒店](https://hotels.ctrip.com/)比较，候选酒店官网核对地址及入住条款 |
| 市内接驳 | [高德地图](https://www.amap.com/) | 车站、机场及地铁官网核对运营要求 |

查询必须填写完整日期、起终点或入住条件，保留具体结果链接和查询时间。首页可访问不代表已获得实时余票、房态或价格。动态网页需要当前端可用的浏览器；受限时明确待核实，不编造结果。

## 冲突与紧迫安排必须先提问

剩余余量按“要求到达时刻−预计到达时刻”计算：要求到达时刻扣除提前到达/候车/值机要求；预计到达时刻包含完整接驳和额外风险缓冲。

- 余量为负：说明冲突及差额，主动询问哪些约束可以调整。
- 余量为0至不足20分钟：即使还能赶上，也主动询问是否更改行程，例如提前出发、换更早班次或协调活动时间。
- 恰好20分钟不因这一阈值单独触发；它不表示一定安全，还需考虑其他不确定性。
- 用户回答前保留原约束，调整后的候选标明待确认；不擅自早退、推迟活动或改为线上参加。
- 用户已确认不可调整的约束不重复询问。同一日程中的紧迫段合并提问；用户接受风险后仍标注紧迫程度。延误重排后再次检查。

例如：徐汇到浦东扣除通勤和缓冲后只剩5分钟，先问“是否调整出发或活动时间”，不能直接将这一段写成稳妥安排。

## 安装与使用

在Codex中发出：

```text
请安装 https://github.com/LouChen-med/plan-daily-travel 中的技能，仓库根目录为技能目录，名称为 plan-daily-travel。
```

也可下载仓库，将整个目录命名为`plan-daily-travel`，放入当前Codex技能目录（通常为`$CODEX_HOME/skills`，未设置时为`~/.codex/skills`）。保持下面的目录结构，安装后在下一轮使用。

```text
plan-daily-travel/
├── SKILL.md
├── README.md
├── references/
│   ├── query-sources.md
│   └── output-format.md
└── scripts/
    └── check_itinerary.py
```

调用示例：

```text
使用 $plan-daily-travel 规划2026年10月6—7日的上海—济南行程。
我将提供每项活动的完整地址及开始、结束时间，每处需提前15分钟到达。
请查询具体班次、最晚出发、缓冲、午餐和酒店，模拟延误30分钟。
如果时间冲突或剩余余量少于20分钟，先询问我是否更改行程。
```

手机、网页和PC端能否直接使用技能、搜索或浏览器，取决于当前端实际支持；没有技能调用能力时，可把所需流程作为Prompt使用，并提供查询页面。安装此技能不自动增加票务API或浏览器权限。

## 时间脚本与边界

`scripts/check_itinerary.py`只计算输入时间，不访问携程、去哪儿或12306，不证明能买到票，也不判断错过固定车次后的新班次。输入说明见[输出模板](references/output-format.md)，网站流程见[查询来源](references/query-sources.md)。脚本需现有Python环境；按使用者的环境规范运行，不自动安装依赖。

技能负责主动提问的流程，脚本的`feasible=true`只表示时间运算未出现负余量，不代表已经满足“小于20分钟先提问”的交互要求或未来交通保证。

本技能提供规划。购票、订房、支付和通知他人需要单独授权。
